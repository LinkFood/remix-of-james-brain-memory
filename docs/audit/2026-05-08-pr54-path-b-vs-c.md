# PR #54 Path B vs Path C decision

**Date:** 2026-05-08
**Author:** Co-Trader / Phase A audit
**Status:** Decision recorded
**Supersedes:** scoping note that recommended Path A (rejected as instance #21 of methodology-errors-cascade)
**Decision:** **Path C with optional pre-commit hook** (Path B deferred, gated on firing-frequency review)

## Context

PR #54 was scoped to make `run_invariant_query`'s "no mid-query semicolon" guard
comment-aware after PR #46 (B-4 hotfix) discovered the guard rejects a valid WITH-CTE
because the guard is a substring search for `;`. Path A — pre-strip comments with a regex —
was caught as the same anti-pattern the rejection is symptomatic of: "reach for a regex
against a thing that needs a real parser." Phase B was blocked.

Decision now is between **Path B** (literal-aware state-machine parser inside
`run_invariant_query`) and **Path C** (no parser change; author discipline plus, optionally,
a pre-commit hook on `query_sql`). Brief's deciding criterion is empirical: **how often does
the parser failure mode actually fire in production?**

**Critical pattern:** every parser-rejection event clusters to the moment a human authored
or edited a `ct_invariants` row. Once an invariant has run cleanly once, it never
spontaneously re-fails. **Zero steady-state firing.**

- **2026-05-01:** 11 rejections in the seed → migration fixup → reseed cycle.
- **2026-05-02:** 2 rejections during warden-warden invariant additions.
- **2026-05-06:** 1 rejection during the B-4 hotfix cycle (fixed in 30 min).

Projected steady-state rate going forward: **<1 event/month** — below the brief's "rare" threshold.

## Vulnerability survey of `ct_invariants`

Pulled all 34 current `ct_invariants.query_sql` rows and audited for the patterns that would
either trip the existing guard *or* be misparsed by Path A's naive comment-strip regex:

| Vulnerable pattern | Count | % of 34 |
|---|---:|---:|
| Line comments (`--`) anywhere | 2 | 6% |
| Block comments (`/* */`) anywhere | 0 | 0% |
| `;` inside a string literal | 0 | 0% |
| Double-quoted identifiers (`"col"`) | 0 | 0% |
| String literal containing `--` or `/*` (would mislead Path A) | 0 | 0% |
| Completely clean (no comments, no semicolon-bearing literals) | 32 | 94% |

Surface is small and stable. The two invariants with line comments have `--` at end-of-line
in WHERE-clauses (not inside literals, no `;`); they pass the guard today.

**Implication:** Path A's risk surface (quoted-string content that looks like a comment,
comment-bearing literals, dollar-quoted SQL) is currently zero. Snapshot, not a guarantee.

## Path B (real state-machine parser) — engineering cost

| Dimension | Estimate |
|---|---|
| PL/pgSQL state-machine parser LOC | 60–90 lines (states: NORMAL, IN_LINE_COMMENT, IN_BLOCK_COMMENT, IN_SINGLE_QUOTE, IN_DOUBLE_QUOTE, IN_DOLLAR_QUOTE) |
| Test categories required | 5: line comment, block comment, single-quote literal containing `;`/`--`, double-quoted identifier, mid-query semicolon outside any quote |
| Edge cases that have already bitten Postgres tooling elsewhere | Dollar-quoted strings (`$tag$ ... $tag$`), nested block comments, escaped quotes in literals (E-strings, `''`-doubling) |
| Maintenance burden | Becomes a critical dependency in the warden read path. Future SQL features (LATERAL, JSON path operators with embedded `;`, `$$`-bodies inside CTEs) all become test-coverage obligations. |
| Performance | Negligible at warden cadence (every 30 min × 34 invariants). Not a real concern. |
| Re-validation risk | Parser bug → `run_invariant_query` raises on a perfectly fine query → silent warden warn-stuck. The thing we just fought twice (B-4, B-3). |

Parser isn't technically hard; the *liability footprint* is the cost. Current guard is
16 lines, trivially reasonable about. A 90-line literal-aware parser imports its own bug class.

## Path C (policy-only) — engineering cost

| Dimension | Estimate |
|---|---|
| Documentation | ~200 words in `docs/SYSTEM_INDEX.md` warden-authoring section: "do not put inline comments in `ct_invariants.query_sql`; do not put `;` outside the trailing terminator (and keep that off — `EXECUTE` doesn't need it); do not use double-quoted identifiers inside the body." |
| Code | None |
| Discipline | Rests on every author of every future invariant — i.e. terminal-Claude-James and any future facet author. No structural enforcement. |
| Failure mode if discipline lapses | Same as today: warden goes warn-stuck on a single invariant until a human notices and edits the row. **Self-healing within 30 min** in every observed instance so far. |

## Path C + pre-commit hook (the lighter mitigation)

A regex grep over the staged diff at PR-time for migrations that touch `ct_invariants` —
flag any `query_sql` whose body contains `--` or non-trailing `;` or `"` outside string literals.
False positives are acceptable (author overrides with a comment in the PR). Cost:

| Dimension | Estimate |
|---|---|
| Hook script LOC | ~30 lines (already have a CI workflow for other migration sanity checks) |
| Coverage | Only catches *migration-authored* invariants. Hot-edits via REST UPDATE bypass the hook — but those are exactly the moments an author is most engaged and most likely to notice the next 30-min warden run. |
| Maintenance | Same author-discipline class as Path C; the hook just flags before merge. |

## Decision

**Adopt Path C, with the pre-commit hook deferred but pre-designed.**

Reasoning, honoring the brief's criterion:

1. Brief defines Path C as sufficient if firing is **rare (<1/month)**.
2. Empirical rate over 5 warden-days: 14 rejections in 7,715 runs (0.18%), all at authoring
   time, **zero steady-state fires post-hotfix**. Projected forward, well below 1/month.
3. Vulnerability surface is small (2/34 = 6% have any comment, 0/34 have hostile literals).
4. Path B's liability footprint — a 90-line parser becoming a critical warden dependency
   capable of class-wide false rejections — is materially worse than today's 16-line guard.
   Trading a known rare failure for an unknown rare failure with larger blast radius.
5. Path C aligns with how the warden actually fails today: within 30 min, visibly, on the
   row being edited, repaired by the editing author. The feedback loop already works.

**Pre-commit hook is queued, not required for adoption** — strictly additive insurance if
Path C ever surprises us (next-90-day firing >1/month).

## What would change the decision

Re-open Path B if any of the following becomes true:

- **Firing frequency rises above 1 event/month** in steady state — i.e. parser rejections
  occurring on invariants that have *previously run cleanly*, indicating a query-pattern not
  covered by author discipline.
- **`ct_invariants` count exceeds ~100** — author-discipline breaks down at scale, and the
  vulnerability surface grows linearly.
- **Warden gains a SQL feature that requires comments in queries** (e.g. dialect-specific
  hint pragmas, dynamic SQL templates with `--noqa`-style markers). Today neither is on the
  roadmap.
- **A single parser rejection ships an invariant warn-stuck for >24h** — current self-heal
  loop is <1h; if the loop ever lengthens, structural enforcement becomes worth Path B's
  cost.
